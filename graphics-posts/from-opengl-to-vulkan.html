From OpenGL to Vulkan

September 6, 2026

I recently ported a basic OpenGL engine to Vulkan (see nebula).
There's already plenty of great resources talking about transitioning from OpenGL to Vulkan:

  • Transitioning from OpenGL to Vulkan by NVIDIA
  • Vulkanised 2023: Use "bindless" to quickly port "bindful" OpenGL apps to Vulkan
  • The journey of porting AnKi to Vulkan
  • NAPTECH: OpenGL to Vulkan
But I wanted to modestly contribute. The goal here is not to provide a detailed guide, but rather offer a few-minutes read to introduce the first principles. Many people still learn graphics programming with OpenGL, and feel overwhelmed by the Vulkan API. I hope this post can help them get started.

What doesn't change

The core ideas of OpenGL are still valid in Vulkan.

  • We still prepare resources like buffers and textures on the CPU, and upload them to the GPU.
  • We can draw things through a rasterization pipeline.
  • This pipeline is configured by pipeline states (blending mode, depth test, backface culling, etc.).
  • We use shaders (vertex, frament, compute...) to program what happens on the GPU.

What does change

OpenGL is a black box, many concepts are hidden and simplified. For the sake of performance and flexibility, Vulkan makes them explicit.

Device choice

OpenGL: You don't choose which GPU to use, the driver decides for you. It is possible to influence this choice, but the API doesn't make GPU selection a central part of the programming model.
Vulkan: We enumerate the available physical devices (GPUs), inspect their capabilities, and then select one to create a logical device from it. This is important for applications that require high performance or predictability.

Scheduling

OpenGL: GPU scheduling is largely managed by the driver. Beginners tend to think that commands like glBindBuffer or glDrawElements are executed immediately, because the API is designed to let you think that. In reality, they are queued and executed later. They might even get reordered, as OpenGL automatically computes a dependency graph and optimizes the workflow.
Vulkan: this mechanism visible instead of hiding it. We record a list of commands into a command buffer, then submit that command buffer to a queue. Nothing runs until we submit it.
We're also responsible for expressing dependencies ourselves: semaphores to order work between frames, fences to know when the CPU can safely reuse or read back a resource, and barriers to insert explicit transitions (e.g. "this image must finish being written before it's read as a shader input").
It's more bookkeeping, but the payoff is that the driver has much less guesswork to do at runtime, and we control how work is organized and submitted.

Resource lifetime

OpenGL resources are managed through handles, and the driver takes care of keeping the underlying objects alive for as long as necessary. We can delete a buffer after issuing a draw call using it and OpenGL will make sure that the deletion doesn't happen while the GPU is still using the buffer.
Vulkan doesn't do this for you. If you destroy a buffer while the GPU still references it, you'll be in trouble. The CPU and GPU work asynchronously, so our Vulkan application needs some form of lifetime management. We handle this with fences (or timeline semaphores): submit work, associate it with a fence, and only destroy or reuse a resource once that fence signals that the corresponding GPU work has completed. In practice, most engines don't check this per-resource; they defer destruction into a small ring of "frames in flight" and only actually free things a few frames later, once they know the GPU has moved past them.

Image layout

TRANSFER_DST_OPTIMAL, SHADER_READ_ONLY_OPTIMAL, etc. Textures in Vulkan aren't just "a texture" the way they are in OpenGL — an image has an explicit layout that describes how its memory is arranged for a given use. TRANSFER_DST_OPTIMAL is the layout we want before copying data into it, SHADER_READ_ONLY_OPTIMAL is what we want before sampling it in a shader, COLOR_ATTACHMENT_OPTIMAL is what we want while rendering into it, and so on. OpenGL quietly rearranges memory for us depending on how a texture is used. Vulkan asks us to say so out loud, via layout transitions inserted as barriers. This is unfamiliar at first, but it maps directly onto something GPUs already do internally (tiling/compression schemes optimized per access pattern) — Vulkan is just making that optimization visible and controllable instead of leaving it to driver heuristics.

Descriptor sets

In OpenGL, binding a resource means calling something like glBindTexture or glBindBufferBase, attaching it to a global binding point that shaders read from implicitly. Vulkan replaces this with descriptor sets: we declare up front, via a descriptor set layout, what kinds of resources (uniform buffers, sampled images, storage buffers...) a shader expects and at which binding slots, then we allocate a descriptor set and write actual resource handles into it before binding the whole set at draw time. It's more ceremony than a single bind call, but it lets the driver validate and compile the pipeline's resource access patterns ahead of time instead of discovering them at draw time, and it lets us swap entire groups of bindings (e.g. per-material or per-frame data) with a single bind instead of many small calls.

Basic Vulkan setup

To get started, you'll need to install the Vulkan SDK. It will provide you some tools like validation layers (API error checking), a SPIR-V compiler, etc. Then I would advise using the following libraries:

  • volk for function loading. It replaces glad or glew for OpenGL.
  • vma to simplify low-level memory management. That part was completely hidden in OpenGL.
  • vk-bootstrap can be a good addition if you want to reduce Vulkan's initialization boilerplate.
  • glfw, glm, stb, tinygltf and imgui which you may have used in OpenGL still work great with Vulkan.
