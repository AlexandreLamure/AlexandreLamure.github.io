From OpenGL to Vulkan

September 6, 2026

I recently ported a basic OpenGL engine to Vulkan (see nebula).
There's already plenty of great resources talking about transitioning from OpenGL to Vulkan:

  • Transitioning from OpenGL to Vulkan by NVIDIA
  • Vulkanised 2023: Use "bindless" to quickly port "bindful" OpenGL apps to Vulkan
  • The journey of porting AnKi to Vulkan
  • NAPTECH: OpenGL to Vulkan
But I wanted to modestly contribute. The goal here is not to provide a detailed guide, but rather offer a few-minutes read to introduce the first principles. Many people still learn graphics programming with OpenGL, and feel overwhelmed by the Vulkan API. I hope this post can help them get started.

What doesn't change

The core ideas of OpenGL are still valid in Vulkan.

  • We prepare resources like buffers and textures on the CPU, and upload them to the GPU.
  • We can draw things through a rasterization pipeline.
  • This pipeline is configured by pipeline states (blending mode, depth test, backface culling, etc.).
  • We use shaders (vertex, fragment, compute...) to program what happens on the GPU.

What does change

OpenGL is a black box, many concepts are hidden and simplified. For the sake of performance and flexibility, Vulkan makes them explicit.

Device choice

OpenGL: You don't choose which GPU to use, the driver decides for you. It is certainly possible to influence this choice, but the API doesn't make GPU selection a central part of the programming model.

Vulkan: We enumerate the available physical devices (GPUs), inspect their capabilities, and then select one to create a logical device from it. This is important for applications that require high performance or predictability.

Click to expand code snippet 
// Enumerate physical devices
uint32_t deviceCount = 0;
vkEnumeratePhysicalDevices(instance, &deviceCount, nullptr);
std::vector<VkPhysicalDevice> physicalDevices(deviceCount);
vkEnumeratePhysicalDevices(instance, &deviceCount, physicalDevices.data());

// Select the best GPU
VkPhysicalDevice physicalDevice = VK_NULL_HANDLE;
for (auto candidate : physicalDevices) {
    VkPhysicalDeviceProperties properties;
    vkGetPhysicalDeviceProperties(candidate, &properties);
    if (properties.deviceType == VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU) {
        physicalDevice = candidate;
        break;
    }
}

// Create a logical device from the selected physical device
VkDevice logicalDevice;
VkDeviceCreateInfo info{ .sType = VK_STRUCTURE_TYPE_DEVICE_CREATE_INFO };
vkCreateDevice(physicalDevice, &info, nullptr, &logicalDevice);

Scheduling

OpenGL: GPU scheduling is largely managed by the driver. Beginners tend to think that commands like glBindBuffer or glDrawElements are executed immediately, because the API is designed to let you think that. In reality, they are queued and executed later. They might even get reordered, as OpenGL automatically computes a dependency graph and optimizes the workflow.

Vulkan: this mechanism isn't hidden anymore. We record a list of commands into a command buffer, then submit that command buffer to a queue. Nothing runs until we submit it.
We're also responsible for expressing dependencies ourselves using barriers, semaphores and fences. It's more bookkeeping, but the payoff is that the driver has much less guesswork to do at runtime, and we control how work is organized and submitted.

Click to expand code snippet 
// Record commands into a command buffer
vkBeginCommandBuffer(commandBuffer, &beginInfo);
vkCmdBindPipeline(commandBuffer, VK_PIPELINE_BIND_POINT_GRAPHICS, pipeline);
vkCmdDrawIndexed(commandBuffer, indexCount, 1, 0, 0, 0);
vkEndCommandBuffer(commandBuffer);

// Submit the command buffer to a queue
vkQueueSubmit(queue, 1, &submitInfo, fence);

Resource lifetime

OpenGL: We can delete a buffer after issuing a draw call using it and OpenGL will make sure that the deletion doesn't happen while the GPU is still using the buffer. The driver takes care of keeping the underlying objects alive for as long as necessary.

Vulkan: The resource lifetime is our responsibility. Destroying a buffer while the GPU still references it means trouble. The CPU and GPU work asynchronously, so we use fences to signal when the GPU has finished using a resource.
In practice, most engines don't check this per-resource. They keep a few frames in flight: while the GPU is still rendering frame N, the CPU is already recording frame N+1 (often 2 or 3 frames overlap this way). Each in-flight frame has its own command buffers and a fence. We only destroy or reuse a resource once that frame's fence signals, so we know the GPU is done with it.

Click to expand code snippet 
constexpr uint32_t FRAMES_IN_FLIGHT = 2;
VkCommandBuffer commandBuffers[FRAMES_IN_FLIGHT];
VkFence fences[FRAMES_IN_FLIGHT]; // One fence per in-flight frame.
VkBuffer uniformBuffers[FRAMES_IN_FLIGHT]; // Resources are duplicated per in-flight frame
uint32_t frame = 0;

// Main loop
while(true) {
    // Wait until the GPU has finished the last submit that used this slot
    vkWaitForFences(device, 1, &fences[frame], VK_TRUE, UINT64_MAX);
    vkResetFences(device, 1, &fences[frame]);

    // Fence signaled: this frame's resources are no longer in use, we can rewrite it
    memcpy(uniformMapped[frame], &camera, sizeof(camera));

    // Submit a command buffer with the frame's fence. The fence will be signaled when the GPU is done with the command buffer.
    vkBeginCommandBuffer(commandBuffers[frame], &beginInfo);
    vkCmdDrawIndexed(commandBuffers[frame], indexCount, 1, 0, 0, 0);
    vkEndCommandBuffer(commandBuffers[frame]);
    vkQueueSubmit(queue, 1, &submitInfo, fences[frame]);

    // Increment the frame index.
    frame = (frame + 1) % FRAMES_IN_FLIGHT;
}

Descriptor sets

OpenGL: Binding resources is a sequence of individual calls. glBindTexture, glBindBufferBase, glUniform*... each one updates a piece of OpenGL's global state machine: a texture unit, a buffer slot, a uniform value.
The currently bound shader then reads from that state.

Vulkan: Resources are grouped into descriptor sets. There is no global binding state. The driver no longer has to reconstruct shader inputs from scattered slots, and we can reuse a set across many draws instead of rebinding everything from scratch.
The usual trick is to split sets by update frequency: one set for data that changes once per frame (camera, lights), another for data that changes per draw or per pass (material textures).
Tiny per-draw values like a model matrix usually go into push constants, a small fast path that doesn't need a descriptor set at all.

Click to expand code snippet 
// Write camera data into the frame descriptor set, once per frame
VkDescriptorSet frameSet;
memcpy(cameraMapped, &camera, sizeof(camera));
VkDescriptorBufferInfo cameraInfo{ .buffer = cameraUBO, .range = VK_WHOLE_SIZE };
VkWriteDescriptorSet frameWrite{
    .sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET,
    .dstSet = frameSet,
    .dstBinding = 0,
    .descriptorCount = 1,
    .descriptorType = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
    .pBufferInfo = &cameraInfo
};
vkUpdateDescriptorSets(device, 1, &frameWrite, 0, nullptr);
vkCmdBindDescriptorSets(cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, layout, 0, 1, &frameSet, 0, nullptr);

for (auto& pass : passes) {
    // Write material textures to the pass descriptor set, once per pass
    VkDescriptorSet passSet = pass.set;
    VkDescriptorImageInfo albedoInfo{
        .sampler = pass.sampler,
        .imageView = pass.albedoView,
        .imageLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL
    };
    VkWriteDescriptorSet passWrite{
        .sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET,
        .dstSet = passSet,
        .dstBinding = 0,
        .descriptorCount = 1,
        .descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
        .pImageInfo = &albedoInfo
    };
    vkUpdateDescriptorSets(device, 1, &passWrite, 0, nullptr);
    vkCmdBindDescriptorSets(cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, layout, 1, 1, &passSet, 0, nullptr);

    for (auto& object : pass.objects) {
        // Write model matrix to push constants, once per object
        vkCmdPushConstants(cmd, layout, VK_SHADER_STAGE_VERTEX_BIT, 0, sizeof(object.model), &object.model);
        // Once all bindings are bound to the command buffer, we can issue the draw call.
        vkCmdDrawIndexed(cmd, object.indexCount, 1, 0, 0, 0);
    }
}

Image layout

OpenGL: A texture is a texture. We don't tell the driver how we intend to use it at a given moment; it rearranges GPU memory behind the scenes.

Vulkan: Images have an explicit layout that must match their current use. TRANSFER_DST_OPTIMAL for uploads, COLOR_ATTACHMENT_OPTIMAL when rendering into them, SHADER_READ_ONLY_OPTIMAL when sampling, PRESENT_SRC_KHR when presenting to the swapchain. We transition from one layout to another with a barrier. Using an image in the wrong layout is a classic source of validation errors (or silent corruption).

Shader compilation

OpenGL: We ship GLSL source and compile it at runtime with glCompileShader / glLinkProgram. The driver turns it into GPU machine code, and reloading a shader can be as simple as reading a text file again.

Vulkan: The API only accepts SPIR-V, an intermediate bytecode. GLSL, HLSL or Slang have to be compiled to SPIR-V first, typically at build time, with a compiler like glslang, DXC or Slang. The driver then consumes SPIR-V. Startup is more predictable, and we get a single IR across vendors, but the "just compile this string" workflow is gone unless we wrap the compiler ourselves.

Basic Vulkan setup

To get started, you'll need to install the Vulkan SDK. It will provide you some tools like validation layers (API error checking), a SPIR-V compiler, etc. Then I would advise using the following libraries:

  • volk for function loading. It replaces glad or glew for OpenGL.
  • vma to simplify low-level memory management. That part was completely hidden in OpenGL.
  • vk-bootstrap can be a good addition if you want to reduce Vulkan's initialization boilerplate.
  • glfw, glm, stb, tinygltf and imgui which you may have used in OpenGL still work great with Vulkan.

Architecture

The rest of the engine shouldn't have to think in Vulkan objects. In nebula I kept an OpenGL-shaped API on top of an explicit Vulkan backend.

A singleton context owns the instance, the device, the swapchain, and two frames in flight. Each frame has its own command buffer, fence, and a deletion queue: when a buffer or image is destroyed, it is only actually released after that frame's fence signals. That is how resource lifetime is handled in practice.

Rendering goes through a small set of functions: beginFrame / endFrame, drawMesh, drawFullscreen, dispatch. A Program is still "the shaders you bind", except that behind it we cache pipeline variants (blend mode, vertex layout, attachment formats). Raster state that used to be glEnable calls is either baked into the pipeline or set as dynamic state.

Resources are bound in two descriptor sets, plus push constants for the rest:

  • Set 0, once per frame: camera UBO, lights, environment cubemap, BRDF LUT.
  • Set 1, per draw or dispatch: a handful of sampled textures and an optional storage image.
  • Push constants, per object: model matrix, material factors, exposure.

That split is the usual answer to "I used to call glUniform for everything".

Render passes use Vulkan 1.3 dynamic rendering, so there is no VkRenderPass / VkFramebuffer object to manage. A thin RAII helper begins rendering, runs the draws, and transitions the attachments to SHADER_READ_ONLY_OPTIMAL so the next pass can sample them. Textures track their current layout, because as we saw, Vulkan will not do it for you.

Memory allocation is delegated to VMA, function loading to volk, shaders compiled from Slang to SPIR-V at build time. The OpenGL-era libraries (glfw, glm, stb, tinygltf, imgui) stay. The result is that scene code and materials still look close to the old engine, while the backend is explicit about queues, layouts, and lifetimes.
